# Private S3 artwork

1. Create an S3 general-purpose bucket in **us-east-1**. Choose a unique name without dots. Keep **all Block Public Access settings enabled**, **Object Ownership: Bucket owner enforced (ACLs disabled)**, and default **SSE-S3** encryption. Use S3 Standard, not Glacier/Standard-IA. No public bucket policy or website hosting is needed.
2. Create an IAM user for the app, without console access. Create a customer-managed policy from `s3-iam-policy.json`, replacing YOUR-BUCKET-NAME with the actual bucket. Attach only that policy. It grants GetObject/PutObject under `duel-artwork/`, without listing, deletion or bucket administration.
3. Create an access key for an application running outside AWS. Put the credentials in local `.env` using the DUEL_S3 variables from `.env.example`, alongside DATABASE_URL. Never commit credentials or send them in chat. Set these same four DUEL_S3 variables in Vercel **after copying the images**. The optional session token is only for temporary credentials. Standard AWS_* names are intentionally avoided because Vercel supplies its own AWS environment.

The CLI expects variables in its process environment; it does not automatically read `.env`. From Bash, load a trusted local .env file without printing it:

```bash
set -a
source .env
set +a
.venv/bin/python manage_hosted.py s3-migrate
.venv/bin/python manage_hosted.py s3-migrate --apply
```

The first command previews; the second creates `duel_artwork_objects` and copies bounded batches to private S3. Uploads include a SHA-256 checksum checked by S3; HEAD verifies size, checksum and content type before the database index is saved. Existing database bytes stay intact. Repeating a migration skips indexed copies. Object keys contain content hashes, so shared URLs cannot be overwritten to show a different image.

Deploy the code, then add the S3 variables to Vercel and redeploy. Confirm image details and thumbnails work in public and admin views and private-folder images remain inaccessible. The browser follows an authorized `/assets/…` redirect directly to S3; Python transfers no image body on this path. Signed links last **120 seconds** and can be shared until they expire. A folder visibility change prevents new links immediately; an existing link may still work for up to 120 seconds. Image bytes already downloaded cannot be recalled. No CORS configuration is needed for normal `<img>` rendering.

Only after the live site is verified, optionally remove the database copies:

```bash
.venv/bin/python manage_hosted.py s3-prune
.venv/bin/python manage_hosted.py s3-prune --apply
```

Pruning compares the current database image SHA-256/size to its index and verifies the corresponding S3 object again before deletion. Missing, changed or unverified copies stay in PostgreSQL. No S3 objects are deleted. Index rows stay so the app knows where the artwork lives. Do not remove S3 configuration after pruning: PostgreSQL no longer contains those image bodies. Keep the bucket and IAM credentials available.

New downloads and new thumbnails are compressed as WebP before upload. Only paths/checksums/sizes remain in PostgreSQL. Each migration batch commits independently; rerunning resumes after completed batches, and renewable leases work with Supabase transaction pooling. The default batch is 25; use `--batch-size 10` for lower memory use on slower machines. Initial copying downloads database images once and incurs S3 PUT/HEAD requests. Pruning computes database hashes server-side, avoiding a second download of the image bodies.
